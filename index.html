01

Reasoning Models vs Frontier + Scaffold

Before reaching for o3 or DeepSeek-R1, consider whether a frontier chat model with a well-designed scaffold achieves the same result. “Scaffold” means explicit chain-of-thought prompting, multi-turn self-critique, best-of-N sampling, or a tool loop.

Hard maths / proofStrong intrinsic; no prompt workModerate; CoT helps but caps out
Latency60s+ for hard problems<5s for most prompts
Cost (hard task)$0.05–$1.20 per query$0.01–$0.10 per query

Open-weight optionYes (DeepSeek-R1 70B)Yes (Llama-3.1-70B-Instruct)
Rule of thumb

If greedy-decode GPT-4o with a zero-shot CoT prompt achieves ≥70% on your target task, a scaffold can likely close the remaining gap more cheaply than switching to a reasoning model. If GPT-4o greedy is below 50%, the task is hard enough that a reasoning model is worth the cost.

Batching and caching strategies

Prompt caching: If multiple queries share a system prompt or document prefix, cache the KV for that prefix. Anthropic charges $0.30/M cached input tokens (vs $3/M uncached for Sonnet 3.7). For a 2k-token system prompt across 10k queries, caching saves ≈$54.

Batch API: OpenAI Batch API gives 50% discount on o-series models with ≤24h SLA. Suitable for offline eval, bulk grading, research pipelines.

Latency is the sharpest constraint on reasoning-model adoption. Thinking tokens are generated sequentially; no parallelism helps. Budget accordingly before choosing a model for an interactive feature.

User experience for long waits

Stream the visible answer even when thinking tokens are hidden. Display a spinner or progress indicator during the reasoning phase. Expose estimated time via stream_options.include_usage if available. Never leave the user with a blank screen for 2+ minutes — acknowledge the task and give an ETA.

04

Tasks Where Reasoning Shines

The defining characteristic of a good reasoning-model task is that the correct answer is: (a) uniquely correct, (b) verifiable, and (c) hard enough that greedy decode fails >30% of the time. These tasks also tend to benefit from planning, self-correction, and exploration of multiple approaches.

Competition Maths

AIME, AMC, Olympiad. Single correct numerical answer. o3 at high effort: 87.3% AIME 2024 pass@1. GPT-4o greedy: 9.3%. Lift: >9×.

Hard Algorithmic Coding

Codeforces Div1-D/E, LeetCode Hard. o1 reaches 89th percentile Codeforces; GPT-4o 11th. Correctness verified by unit tests. Multiple sub-problems benefit from backtracking.

Formal Proof & Verification

Lean 4 / Isabelle proof generation. Reasoning models discover proof sketches that a greedy model abandons after one failed attempt. ARC-AGI (abstract pattern extrapolation) also fits this regime.

Multi-Step Planning

Long-horizon agent tasks where the plan must be revised mid-execution. Reasoning traces naturally encode plan → action → observe → revise. Reduces number of outer agent loop turns needed.

Scientific / Graduate-Level QA

GPQA Diamond (PhD-level questions): o3-mini 79.7% vs GPT-4o 53.6%. Questions require combining multiple sub-domain facts and holding uncertainty across steps.

Hard Constraint Satisfaction

Scheduling, bin-packing, graph colouring at moderate scale. Model can enumerate and reject infeasible assignments internally. Reduces need for external solvers on small instances.

05

Tasks Where It Doesn't

Reasoning models incur real costs for their extended thinking — latency, token spend, and sometimes quality regression. For these task types, a well-tuned frontier chat model reliably wins.

Conversational Chat & Customer Support

Tone, empathy, concision, and rapid back-and-forth dominate quality. Reasoning models can over-plan, producing terse or mechanical responses. RLHF-tuned chat models (Claude 3.5 Sonnet, GPT-4o) score higher on MT-Bench and human preference evals.

Simple Code Autocomplete

Single-function completion at the editor cursor. Correct answer is usually obvious from context; a small fast model (Codestral, Haiku) serves <100ms. Waiting 30s for an o3-mini response is a UX failure.

Creative Writing & Poetry

No single correct answer. RL reward signal (correctness) is not defined here. Reasoning models frequently produce stilted, over-structured prose. Prefer Claude 3.5 Sonnet, GPT-4o with a creativity-oriented system prompt.

Factual RAG Retrieval Answers

When retrieved passages contain the answer, a reasoning model adds latency without accuracy gain. The bottleneck is retrieval recall, not reasoning depth. GPT-4o with citations is the right tool.

The “over-thinking” failure mode

On simple questions, reasoning models sometimes emit thousands of thinking tokens second-guessing themselves, then produce a worse answer than greedy decode. OpenAI's reasoning_effort: low (or analogous budget_tokens: 512 in Anthropic's API) mitigates this. If you observe regressions on easy tasks when switching to a reasoning model, reduce the thinking budget first before abandoning the model class entirely.

06

Hybrid Pipelines — Fast Model with Reasoning Fallback

The most production-practical architecture combines a fast cheap model for the common case with a reasoning fallback for hard cases. The challenge is routing: how do you decide which path a query takes?

Incoming query
↓
Router (classifier or heuristic)
↓
Easy? → Fast path: GPT-4o-mini / Haiku, <2s, $0.001
↓ (hard or uncertain)
Confidence check: did fast model self-rate confidence ≥0.8?
↓ (low confidence)
Slow path: o3-mini / Claude 3.7 Sonnet, 30–90s, $0.05–$0.20
↓
Return answer to user

Router strategies

Rule-based routing

Keywords, token count, or task type tag trigger the slow path. Simple, predictable cost. Example: any query containing “prove”, “algorithm complexity”, or “optimise for” → slow path.

Confidence-based routing

Run fast model first; if its self-rated confidence (in a structured output field) is below threshold, escalate. Cost = fast model always + slow model on escalated fraction.

Small classifier router

Fine-tune a BERT-class model on (query, “hard”/“easy”) pairs from historical logs. Adds <50ms latency. RouteLLM (Ong et al., 2024) showed 40% cost reduction with 95% quality retention this way.

07

Reasoning + Tools — Long Traces with Tool Calls Interleaved

Modern reasoning model APIs support interleaving thinking blocks with tool use within a single model turn. This is qualitatively different from classic ReAct: the model can think → call tool → think about the result → call another tool, all before emitting any visible content.

Anthropic API — extended thinking + tool use (Claude 3.7 Sonnet)
import anthropic
client = anthropic.Anthropic()

tools = [{
    "name": "run_python",
    "description": "Execute Python code and return stdout.",
    "input_schema": {
        "type": "object",
        "properties": {"code": {"type": "string"}},
        "required": ["code"]
    }
}]

resp = client.messages.create(
    model="claude-3-7-sonnet-20250219",
    max_tokens=8000,
    thinking={"type": "enabled", "budget_tokens": 5000},
    tools=tools,
    messages=[{
        "role": "user",
        "content": "Find the smallest prime > 1e9 and verify with a sieve."
    }]
)
# Response may contain: [ThinkingBlock, ToolUseBlock, ThinkingBlock, TextBlock]
for block in resp.content:
    print(block.type, getattr(block, 'text', '')[:80])
Context budget management in tool loops

Each tool result appended to the conversation consumes context. With 5k thinking tokens per turn and 2k tool results, a 128k-context model exhausts context in ∼20 tool turns. Practical mitigations: (1) summarise completed sub-tasks before continuing; (2) limit tool-result verbosity; (3) use a sliding-window that keeps the last N=5 turns; (4) checkpoint the agent state to a database and resume from a fresh context when needed.

Thinking blocks must be echoed back

In multi-turn agentic conversations with Claude extended thinking, thinking blocks must be returned verbatim in subsequent user turns when the model paused mid-generation for a tool call. The API rejects conversations that omit them. This increases per-turn prompt size significantly for long agent sessions.

08

The Future Direction

Reasoning models in 2025 are still a young paradigm. Several active research and engineering directions will significantly change the deployment picture within 12–24 months.

Faster thinking tokens

Speculative decoding applied to thinking traces. Draft-verify with a small model for the reasoning portion; full model only for the visible answer. Early results show 2–3× latency reduction with <1% accuracy drop. Google DeepMind and Groq are both working in this area.

Compressed / cached traces

Reuse the thinking-token KV cache across turns in an agentic loop. If the context hasn't changed, the model shouldn't re-derive the same sub-conclusions. Prefix caching for reasoning prefixes is already partially available on Anthropic's API.

Smaller reasoning models

DeepSeek-R1 7B and 14B distillations already outperform GPT-4o on MATH. Quantised versions (Q4_K_M via llama.cpp) run on a single A100 at ≈40 tok/s. Local deployment of reasoning models is practical today for maths and coding tasks.

Reasoning + retrieval

The model reasons about what to retrieve mid-trace, issues retrieval calls, incorporates results, and revises its understanding — all before answering. DeepResearch-style agents already exhibit this. The open question is how to bound latency when retrieval is in the critical path of a thinking trace.

One trend to watch: reasoning as a training signal

Reasoning traces generated by o3/R1 are being used as synthetic training data for the next generation of smaller models. Distillation from thinking traces — not just answers — produces models with significantly better reasoning than distillation from answers alone (the “process-level distillation” approach). This may commoditise medium-hard reasoning within 18 months.

09

What to Take Away

  • Use reasoning models when greedy fails. The practical threshold: if your best frontier chat model with a CoT prompt scores below ≈50% on a task category, switch to a reasoning model. Above 70%, a scaffold is usually cheaper.
  • Match latency budget to product reality. Interactive features need <10s TTFT — that rules out o3 at high effort. Batch pipelines, research tools, and async agents have no such constraint. Segment your use cases.
  • Cost grows with difficulty, not just token length. Hard problems spend 10–100× more reasoning tokens than easy ones. Profile representative queries before committing to per-query pricing. Use reasoning_effort: low as a baseline and promote only where needed.
  • Hybrid routing saves 40–60% cost with minimal quality loss. Route easy queries to a fast model; escalate to reasoning only on hard cases. RouteLLM-style classifiers can automate this with <50ms overhead.
  • Tool-interleaved thinking is powerful but context-hungry. Echo thinking blocks back on every turn; summarise completed sub-tasks; use sliding-window context management for multi-step agents.
  • Open-weight reasoning is viable today. DeepSeek-R1 70B at Q4 quantisation runs on 2×A100 80GB. For maths and coding, it matches o1-level performance at near-zero per-query cost once hardware is amortised.
The decision in one sentence

Use a reasoning model when the task is hard, verifiable, and latency-tolerant. Use a frontier chat model (with a scaffold if needed) for everything else. Invest in hybrid routing to get the best of both worlds in production.
